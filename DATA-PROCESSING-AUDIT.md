# Аудит обработки данных Book Meet Club

Дата проверки: 16 августа 2026 года. Объект: production-домен `bookmeet.club`, приложение Node.js/Express, MySQL/MariaDB и панель Hoster/Plesk. Этот документ фиксирует проверяемые технические факты, а не является юридическим заключением.

Каноническая текущая карта хранения и ownership — [docs/codex/DATA_MODEL.md](./docs/codex/DATA_MODEL.md); интеграционные границы — [docs/codex/INTEGRATIONS.md](./docs/codex/INTEGRATIONS.md). Этот audit не переписывается в рамках Codex-навигации.

## 1. Категории данных и места хранения

| Категория | Где хранится | Назначение | Технический доступ |
|---|---|---|---|
| Учетная запись | `users`: e-mail, хеш пароля, Google subject, Telegram subject, роль, статус удаления | вход, восстановление, связь профиля | приложение; администратор БД |
| Профиль | `profiles`: имя, город, дата рождения, пол, текст анкеты, настройки | профиль, возрастные ограничения, подбор контента | профильные API; часть полей публична по правилам видимости |
| Социальные связи | `friendships`, `friend_requests`, `follows`, `community_memberships`, `user_blocks` | дружба, подписки, сообщества, блокировки | только авторизованные API с серверной проверкой |
| Контент | книги, рецензии, публикации, комментарии, события, поводы, новости издательств | основная работа платформы | публичный или авторизованный доступ по типу и статусу материала |
| Сообщения | `messages` и вложения | личные и служебные диалоги | участники диалога и администраторская поддержка по серверным правилам |
| Вишлист | `wishlist_items`, приватные данные получателя | подарок другу | владелец и подтвержденные друзья; не возвращается гостям и подписчикам |
| Жалобы и модерация | `reports`, `report_status_history`, `report_appeals`, `moderation_audit_log` | рассмотрение жалоб и доказуемость действий | заявитель видит свои жалобы; административные действия только администратору |
| Безопасность | `sessions`, `login_attempts`, `security_event_log`, `security_incidents` | сессии, brute force, расследование инцидентов | только сервер и администратор |
| Юридические согласия | `legal_documents`, `legal_acceptances` | версия и факт принятия обязательных документов | пользовательский gate; публикация и аудит только администратору |

Пароли хранятся как `scrypt`-хеши с индивидуальной солью. Сессионный токен находится только в cookie браузера; в БД сохраняется SHA-256-хеш токена. Cookie имеет `HttpOnly`, `SameSite=Lax` и `Secure` в production.

## 2. Возраст и доступ 18+

Возраст не хранится отдельным полем: он вычисляется из даты рождения при каждом чтении/проверке. Сервер запрещает прямую дружбу и личные сообщения между группами `<18` и `18+`; сообщества и администраторская поддержка обрабатываются отдельными правилами. Запросы карточек и вложений 18+ проверяются на сервере, а не только скрываются интерфейсом.

После перехода возрастной границы выполняется повторная серверная проверка существующих связей. Миграция не меняет дату рождения и не требует ручного переключения статуса.

## 3. Юридические документы

Каждая активная версия имеет тип, версию, язык, текст, имя исходного файла, дату публикации и флаг повторного принятия. Принятие записывает пользователя, документ, тип, версию, язык и UTC-время. Регистрация не завершается без трех опубликованных обязательных документов и двух явных unchecked-by-default согласий.

Юридические тексты не включены в код и должны быть опубликованы администратором отдельно на русском, казахском и английском языках. До публикации полного набора новая регистрация закрыта с безопасной ошибкой конфигурации.

## 4. Google OAuth

- Запрашиваемые scopes: `openid email profile`.
- Фактически используются: `sub`, подтвержденный `email`, `name`, `aud`, `nonce`.
- В БД сохраняются Google `sub` (`google_subject`), e-mail и отображаемое имя.
- Access token получается только в legacy authorization-code callback как часть ответа Google и не записывается в БД, файл или cookie. Refresh token не запрашивается и не сохраняется.
- Основной Google Identity Services flow проверяет ID token; сырой ID token не сохраняется.
- Удаление аккаунта очищает `google_subject`; окончательно удаленный профиль нельзя связать с новым аккаунтом.

Legacy callback больше не создает новую учетную запись без юридических согласий: для новой регистрации используется credential flow с теми же обязательными согласиями, что и для пароля.

## 5. Telegram

Администраторский бот получает только тип события, внутренний ID и краткое описание:

- обращение в поддержку — служебная фраза без текста сообщения;
- событие/повод на модерации — название или основной текст материала;
- анкета организации — название профиля;
- жалоба — тип объекта без причины и содержимого жалобы.

Текст личных сообщений не передается. Токен бота и chat ID находятся только в переменных окружения. Outbox хранит тип события, ID сущности, ID инициатора, краткое описание, попытки и техническую ошибку доставки; секрет Telegram из ошибок удаляется.

Для будущих пользовательских уведомлений добавлены отдельный opt-in, список категорий и отключение/отвязка Telegram. Сам факт наличия полей и API не означает, что пользовательский Telegram-flow уже запущен: до запуска нужна отдельная подтвержденная привязка Telegram ID и продуктовый интерфейс подключения.

## 6. Профили издательств и партнеров

БИН, расчетный счет, БИК, банк, юридический и почтовый адрес не возвращаются публичному API и не включаются в guest catalog. После этой проверки они возвращаются bootstrap-сериализатором только администратору. При обычном редактировании издательского профиля сервер сохраняет уже записанные закрытые поля, не раскрывая их обратно владельцу.

## 7. Логи

### Приложение

Express не ведет общий access-log каждого запроса. В stdout/stderr записываются запуск/остановка, необработанные ошибки и обезличенные ошибки Telegram. Cookie, сессионные токены и пароли намеренно не журналируются.

Новый `security_event_log` записывает UTC-время, ID пользователя при наличии, тип/результат события и HMAC-SHA-256 IP/User-Agent. Сырые IP и User-Agent в эту таблицу не попадают. Для хеширования требуется отдельный `AUDIT_HASH_SECRET` в production.

### Plesk и веб-сервер

В панели подтверждены webserver-записи с полями: дата/время, тип, исходный IP, HTTP-код, метод и URL, User-Agent, размер ответа и источник журнала Apache SSL/TLS. Интерфейс также предусматривает referrer. ID пользователя приложения, тело запроса, cookies и session ID в показанных строках не обнаружены.

Журнал операций Plesk содержит дату/время, сырой IP, пользователя панели, тип операции и объект. На 16.08.2026 в нем доступны записи как минимум с 16.03.2026, то есть фактическое наличие данных подтверждено минимум за пять месяцев. Настройка окончательного срока хранения в доступной панели не показана.

Период ротации webserver-логов, защита архивов логов и круг лиц с серверным доступом должны быть подтверждены у Hoster/Plesk. До подтверждения нельзя считать эти параметры соответствующими внутренней политике.

## 8. Резервные копии Hoster/Plesk

На 16.08.2026 для `bot.oqyastana.kz` видны две серверные резервные копии:

- 14.08.2026 03:12 — 652 МБ;
- 07.08.2026 03:09 — 369 МБ.

Обе помечены «Все настройки и контент». Экран восстановления подтверждает наличие учетных записей почты, баз данных, SSL/TLS-сертификатов, сайтов, DNS-зоны и файлов домена. Следовательно, копии содержат и MySQL, и загруженные пользователями файлы. Копии размещены на сервере Plesk; доступны учетной записи подписки и администраторам провайдера в рамках их полномочий.

Шифрование резервных копий, отдельное шифрование ключей и формально настроенное число сохраняемых поколений в доступном интерфейсе не подтверждены. Наличие двух недельных копий показывает наблюдаемую, но не гарантированную политикой глубину в семь дней между снимками и минимум две точки восстановления.

Для `bookmeet.club` прямой переход к manager domain ID вернул `Access to the foreign subscription is denied`, поэтому отдельная backup-политика нового домена текущей учетной записью не подтверждена. Видимый нулевой объем `bookmeet.club` и размещение проекта в `httpdocs/bot` старого домена указывают, что production-файлы и копии по-прежнему учитываются в подписке `bot.oqyastana.kz`.

### Обязательная процедура восстановления

1. Старую копию никогда не подключать как постоянную рабочую БД без post-restore процедуры.
2. До восстановления выгрузить актуальный реестр `finalized_profile_deletions` в защищенное хранилище вне восстанавливаемой копии.
3. После восстановления повторно обезличить/удалить все аккаунты из актуального реестра, отозвать их сессии и Google/Telegram identifiers.
4. Проверить, что жалобы и сообщения сохранены только в обезличенном виде, а публичное авторство отображается как «Удаленный пользователь».
5. Только после проверки открывать восстановленный экземпляр для пользовательского трафика.

## 9. Сроки хранения

| Данные | Реализованный срок/условие |
|---|---|
| Обычная сессия | `SESSION_DAYS`, сейчас пример конфигурации — 7 дней |
| Административная сессия | `ADMIN_SESSION_HOURS`, по умолчанию 12 часов |
| Удаляемый профиль | 15 дней на восстановление, затем обезличивание/окончательная очистка |
| Жалобы, история статусов, мотивированные ответы | сохраняются обезличенными после удаления заявителя |
| Публичные материалы и необходимые сообщения | сохраняются с tombstone-автором для целостности |
| Security event log / moderation audit | автоматическая очистка пока не настроена; срок должен быть утвержден политикой |
| Plesk action log | подтверждено наличие минимум за 5 месяцев; предел не установлен в доступной панели |
| Backup | наблюдаются 2 недельных снимка; формальная ротация и шифрование не подтверждены |

## 10. Открытые организационные риски

1. Утвердить юридические тексты и версии по каждому языку; приложение не генерирует их самостоятельно.
2. Установить уникальный `AUDIT_HASH_SECRET`, не совпадающий с DB/SMTP/Telegram секретами.
3. Получить у Hoster подтверждение шифрования backup, точной ротации, доступа сотрудников и сроков хранения webserver/Plesk логов.
4. Хранить актуальный реестр окончательных удалений отдельно от циклических backup и включить post-restore проверку в регламент.
5. Назначить внутренние сроки удаления security/moderation logs и документировать законное основание хранения.
6. Перед production-публикацией применить миграцию `030_legal_safety_compliance.sql`, затем опубликовать полный комплект документов; код и миграция должны выпускаться в таком порядке, чтобы не блокировать существующий вход.
