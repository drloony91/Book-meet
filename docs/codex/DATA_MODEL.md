# Data model

Source of truth: `mysql/migrations/001_initial.sql` … `055_reading_presence_visibility.sql`. `scripts/migrate.js` applies sorted files and records `schema_migrations`; it splits statements and must not be used to rewrite an applied migration. `server/data.js` is the read/DTO projection layer. Nullable below means the current schema accepts `NULL`; JSON/LONGTEXT empty defaults are separate from SQL null.

## Social content (queue 4)

`043_social_content.sql` extends `material_comments` with a root parent, exact reply target, tombstone and update metadata. `material_comment_likes` has an idempotent `(comment_id,user_id)` key. `content_mentions` stores stable user IDs by polymorphic entity rather than reparsing usernames. `reposts` normalizes sources to an original material and has a nullable clean-source key so only clean reposts are unique per user/source. Text repost provenance is private in nullable `excerpts.provenance_repost_id` and is never part of public excerpt DTOs.

Real-schema verification runs through the disposable Docker Compose MySQL 8.4.11 fixture (`compose.mysql-test.yml`), isolated as `book_meet_test` on `127.0.0.1:3307`. It validates the final schema and ledger against the real engine; it never targets production configuration or credentials. On 2026-09-16 `pnpm verify:db` passed the complete clean-schema, repeat-run, seed, transaction, queue-3/4/5 HTTP, relational and A-01 recovery suite and removed its container and named data volume afterward.

Migration `038` also removes historical `new_message` rows from the general notification center. New personal messages retain unread/read state only in `messages`; they no longer create `notifications` rows.

Migration `044` adds one `like` reaction per message/user pair. Bootstrap loads reactions in one batch restricted to the already selected visible message IDs and projects `likeCount`, `likedByViewer` and participant-only `likedByUserIds` on each message DTO.

Migration `045` adds `messages.edited_at` and a closed edit-evidence table. A text-only, non-system message may be edited only by its author while the pair remains accessible and the author has not cleared it. Each mutation stores the previous body and atomically replaces message mention links; ordinary participant DTOs expose only the current body, mentions and `editedAt`.

Migration `049` adds the InnoDB `FULLTEXT(body)` index used by both message-search APIs. Search requires every normalized token as a boolean prefix, rejects tokens shorter than three characters, and does not perform Russian stemming: a user must enter the stored word or a prefix of at least three characters. Queries read only `messages.body`; edit/deletion evidence is never joined, deleted rows are excluded, and each viewer's `chat_history_clears` boundary remains authoritative.

Migration `046` defines the canonical notification categories (`friendships_follows`, `likes`, `comments_replies`, `mentions`, `reposts`, `events_communities`, `reading_reminders`, `system_security`). Unknown future types fail safe into `system_security`. External preferences can be enabled only after separate delivery readiness and verified account state; the legacy Telegram subject and structurally configured SMTP are not proof. Legacy Telegram notification routes are compatibility adapters over normalized preferences. Disconnect clears the verified delivery binding and all normalized Telegram channel selections transactionally, but deliberately retains `telegram_subject` because it remains an authentication identity. Stage 3A does not add delivery outboxes or sends.

Migration `047` makes `notification_events` the sole production creation boundary and `notification_deliveries` the generic user-channel outbox. Event creation, selected in-app projection and delivered in-app job are atomic; repeated recipient/dedupe keys create nothing twice. Telegram/email jobs exist only when both the normalized category preference and verified readiness are effective. Disabling a category/channel, Telegram disconnect, and material deletion cancel only pending/failed external jobs; event evidence remains. Daily email is scheduled for the next 09:00 in the user's effective IANA timezone. The worker receives only a generic category title, safe summary and optional material link metadata, never the internal body by default.

Migration `051` adds the hashed, 15-minute, one-time Telegram binding token, a safe display label and a delivery-error timestamp. The webhook is authenticated with its own secret; `/start` binds the numeric Telegram identity without accepting a username/chat ID from the browser. A Telegram 403 marks the channel as errored, disables normalized Telegram selections and cancels pending jobs; successful user-initiated retest clears the error but never re-enables categories automatically. Signed email unsubscribe links disable only optional email modes and cancel pending email deliveries; in-app system/security notifications remain mandatory.

Migration `052` is the Part A1 additive compatibility stop point for the common conversation model. It creates `conversations`/`conversation_members`, nullable `messages.conversation_id`, and backfills one direct conversation per recoverable unordered pair before adding active membership only for users with both `deleted_at` and `purged_at` null. Sender-null tombstones use `message_deletion_evidence.sender_reference_id` when present; this preserves deterministic historical pairing without reviving a deleted account. Any message without recoverable pair identity, or an invalid self-pair, is recorded in durable `conversation_backfill_orphans` with stable references and deliberately remains outside the future conversation access boundary. The migration creates exactly one closed, no-FK `conversation_backfill_reconciliations` record whose source/mapped/orphan invariant is enforced by the database for release audit even after later data deletion. No direct API/query/write path switches in this migration, no legacy column is dropped, and there is no group/marketplace surface until later separately gated stages.

Migration `053` adds audited session operators, per-member group read boundaries, group-message foundations, poll/options/votes and closed moderation evidence. Each `conversation_polls` row is uniquely tied to a server-created system `messages` row, so it participates in chronology and becomes invisible through the ordinary global-clear boundary. Poll options carry a composite `(poll_id,id)` key and votes reference that pair, which prevents a cross-poll option id from being persisted. Group messages keep legacy direct columns but use nullable `recipient_user_id`; legacy social projection explicitly excludes non-direct conversations. A group history clear moves the conversation boundary without deleting evidence, and every current member's read/unread boundary is `max(last_read_message_id, history_cleared_message_id)`. `group_message_moderation_evidence` keeps stable message, author and deleter references plus original text/kind/sticker/attachment beside nullable live FKs, so owner/moderator deletion survives account deletion and never enters ordinary DTOs or full-text search. The server feature remains closed unless `BOOK_MEET_GROUP_CHATS_ENABLED` is exactly `1` or `true`.

`035_community_book_month.sql` adds nullable `user_books.featured_month` and `featured_year` for community-only catalogue associations; the pair is either both null or a valid month/year. `036_privacy_friends_defaults.sql` makes birth-date and social visibility default to `friends` and normalizes existing profiles.

## Moderation, legal and operational records

`reports` references reporter/target/reviewer; reporter was deliberately made nullable and `SET NULL` in `030` to preserve anonymized moderation evidence. `report_status_history` and `report_appeals` cascade with report; actor/appellant/reviewer are nullable and set null. `moderation_audit_log` keeps admin/report references nullable and set null. `security_event_log` and `security_incidents` retain nullable user/admin references; `finalized_profile_deletions` is a user tombstone with unique hash. See `017`, `030`, `031` and `server/modules/compliance.js`.

`legal_documents` has required type/version/language/content metadata and nullable uploader; `(document_type, version, language_code)` is unique. `legal_acceptances` requires user/document and cascades user but **restricts document deletion**. Community moderation legal documents are distinct from mandatory registration acceptance (`031`).

`telegram_alert_outbox` stores required event/entity/dedupe fields plus nullable actor, summary, lock/delivery/error timestamps; actor deletion sets null (`027`). `schema_migrations` is the canonical runner ledger, not application data. `schema_migration_attempts` is a separate operational diagnostic ledger: before an unapplied migration runs, the runner records a durable `running`/`failed` marker with the 1-based statement position, preview, engine error and timestamps. It is deleted only after the canonical migration row is committed; a stale/failed marker without a canonical row blocks blind rerun.

`tests/mysql-integration.test.mjs` applies all production migrations on a clean `book_meet_test`, compares the complete sorted ledger, reruns the actual runner as a no-op, and checks real late columns and representative foreign-key behavior. Its A-01 fixture is deliberately separate at `tests/fixtures/mysql-migrations/`: it models an idempotent first DDL followed by an absent required dependency, then verifies the diagnostic block and only-marker retry after explicit reconciliation. The unsafe behavior was reproduced on isolated MariaDB 10.6.27, and the durable diagnostic/recovery gate was subsequently verified end to end on disposable MySQL 8.4.11.

## Deletion and nullability rules

Foreign-key cascades remove user-owned operational rows, while content links that must survive an account/content deletion use `SET NULL`; report/legal records intentionally preserve evidence. Polymorphic material tables have no database-level target FK, so every read/write path must use server authorization and age/privacy helpers. For a complete field list consult the migration file named above; do not infer schema from client DTO optionality.

The deterministic migration/file and `CREATE TABLE`/`ALTER TABLE` inventory is generated in [generated/SCHEMA.md](./generated/SCHEMA.md). Run `pnpm docs:check` to detect stale output; keep field semantics and ownership in this document.

## Progress notes (queue 3, stage 2)

Migration `041_book_progress_notes.sql` stores 1–3000-character note bodies and immutable active-unit progress snapshots. Users/books cascade to notes; deleting a reading cycle sets only the cycle reference to NULL. The source of the snapshot is the locked personal `user_books` row; client `expectedProgress` is a precondition, never the saved source. Owner text edits preserve all progress columns. Account finalization explicitly removes notes because user rows survive as tombstones.

The same migration adds `user_hides(hider_user_id, hidden_user_id, created_at)` as the persistence/filter foundation shared with the following social queue. This queue filters seeded/existing hide relations for new materials; the public hide controls/endpoints remain part of queue 4. Both users cascade, and self-hide is forbidden.

Note bodies are selected only after the SQL viewer predicate: own notes, completed readers, or snapshots up to the active saved percentage. Missing/unknown progress and `want` allow only zero percent. Blocks, hidden authors, deleted authors and book age restrictions apply before serialization. `book_note` is a reporting target, not a reaction/comment/save kind. Admin report projections alone include note text and the parent book ID.

## Book shelves (queue 3, stage 3)

Migration `042_book_shelves.sql` stores reader-owned public shelves and their ordered items. Creation and editing lock the owner library rows and replace the item set in one transaction; every selected canonical book must already belong to that reader. Deleting a catalogue book keeps the shelf position but exposes an unavailable item. Deleting a shelf explicitly removes polymorphic likes, saves, comments and notifications because those tables cannot carry a target foreign key.

Shelf reads apply deleted-account, bidirectional block, one-way hide and per-book 18+ rules before serialization. Restricted or unavailable items expose neither a book ID nor book data. Batch addition locks the shelf and caller library, inserts only absent readable books as `want`, preserves every existing status and returns authoritative added/skipped counts. `material_saves.material_kind` includes `shelf`; the other material-action tables already use string kinds.
